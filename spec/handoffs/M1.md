## Rulings new in this handoff (spec authority, pre-answered)

These would otherwise be your QUESTIONS.md entries; they are decided:

1. **Worldgen is COPIED, not cross-imported.** The v1 chain is ported
   verbatim into `v2/src/ported/worldgen/` (per the build plan's
   `ported/` doctrine). Each file carries a citation header: v1 path,
   the v1 commit hash you copied from, and a list of every deviation.
   v2 never imports from the repo root; v1 stays untouched and
   runnable.
2. **Ported worldgen stays JavaScript.** Verbatim behavior outranks
   TypeScript purity — hand-converting ~2000 lines invites
   transcription bugs. Ported files remain `.js` (ESM) behind a typed
   boundary (`adapter.ts`, see deliverable 2) which is the ONLY thing
   the sim imports. The sim-directory eslint restrictions do not apply
   inside `src/ported/worldgen/` — **except** as ruling 3 requires.
3. **Transcendentals in ported code must be swapped.** The substrate
   feeds the world hash, and the tri-engine gate requires bit-identity
   — so any `Math.sin|cos|tan|exp|log|pow|atan|atan2|asin|acos|sinh|
   cosh|tanh` in ported worldgen code is mechanically replaced with the
   dmath equivalent, and every swap is listed in that file's citation
   header. Consequence for the oracle test (deliverable 2): fields
   untouched by any swap compare bit-exact against v1; fields
   downstream of a swap compare within 1e-6 relative. `Math.sqrt/abs/
   min/max/floor/ceil/round/trunc/sign` are IEEE-exact and stay.
4. **The M0 placeholder tick survives M1.** M0.md promised its deletion
   at M1, but M1 adds no dynamic conserved field (people is M2, food is
   M3), and the conservation harness and determinism smoke need a live
   exerciser. It survives, still clearly marked, and dies at M2. What
   M1's tick DOES add honestly: the calendar — a month counter
   (12-cycle) that drives seasonal cost customization. The calendar is
   a clock for physics inputs (monthly climate), never a content gate
   (R1).
5. **Do not materialize every cost metric.** 12 months × modes ×
   directed edges at 1800×900 is gigabytes. The engine stores per-cell
   terrain/climate components and customizes a metric on demand
   (active month + mode set), with a small explicit cache of customized
   metrics. Full recustomization on cache miss is acceptable at M1 if
   it fits budget; dirty-region invalidation can wait for a consumer
   that dirties regions (roads, M7).
6. **Multimodal routing is a layered graph.** A journey switches modes
   (walk to the port, sail, walk again): the query graph is
   (cell × mode) layers with transfer edges where legal (ports/coast
   cells for land↔sea, river-adjacent cells for land↔river). Taking a
   per-edge min over modes is FORBIDDEN — it teleports a traveler
   between modes mid-desert and will pass no ORBIS check honestly.
7. **Capabilities are query parameters at M1.** Mode availability is
   capability-gated (pack animals, wheels+draft, boats, navigation),
   but the technique field that grounds capabilities in-world arrives
   at M2. Until then the query interface takes an explicit capability
   set; the gate battery pins the historically appropriate set per
   route. No date ever gates a mode (R1).
8. **Perf budgets arm as a ratchet.** First honest measurements land in
   a committed `v2/bench-baselines.json` (per grid, per phase); CI
   fails any >20% regression against the committed baseline. Working
   targets (misses are QUESTIONS.md findings, never fudges): preprocess
   ≤ 60 s at target grid; customize ≤ 2 s per metric; point query
   ≤ 5 ms; full multi-source distance map ≤ 500 ms.

## Deliverables

### 1. The grids, re-founded

`target` becomes **1800×900** (~22 km at the equator; ~0.5M land
cells); `dev` stays 240×120. This is the shipped configuration every
gate runs at (R3) — there is no third "gate grid". Bench baselines are
set fresh at these dims. `SAVE_VERSION` bumps to 2 (grid semantics
changed; v2 carries no legacy saves — no compatibility shims).

### 2. The worldgen adapter — `src/ported/worldgen/` + `src/sim/substrate.ts`

Port the v1 chain per the dossier's verdicts: `worldgenUtils.js`,
`earthData.js` (the 1920×960 DEM — bilinear sampling is grid-free),
`worldgen.js`, `tectonicGen.js`, `windSolver.js`, `moistureSolver.js`,
`riverGen.js`, `biomeClass.js`, `cropGen.js`, `cropPackages.js`,
`resourceGen.js`, and the substrate-relevant parts of `pipeline.js`
(`buildWorld`, `buildTerritory`). Resolve the four backward imports
exactly as the dossier prescribes (carry `mkRng`/`hash32` from the M0
port; carry `baseEdgeCost` from deliverable 3 — the dossier notes it is
deliberate that worldgen's tCross equals the sim's transport cost; cut
or inline the `T` lever imports with the value cited in the header).

`substrate.ts` is the typed boundary: `buildSubstrate(seed, config,
grid) → Substrate` — elevation, land mask, **monthly** climate
(temperature/moisture per month — do NOT collapse to annual; v1 mostly
did and 03 explicitly wants the seasonality), rivers (magnitude,
downstream direction), lakes, floodplains, biomes, soils/fertility,
wild-crop ranges, resources, relief, coast distance. All typed arrays,
SoA. The substrate is **immutable and never saved** — rebuilt from
seed + config (config identity is already part of world identity).
The earth-corrections stay a labeled data stage, excluded from
procedural presets (R7).

Port-with-cleanup items (dossier §worldgen): extract the peopleSim
imports; keep physical-units floodplains as the only branch; convert
the flagged per-tile constants (lake cap, mine scatter radii, ancestry
hops) to km, citing the dossier's scar list. The module-level PERM
table (one world per process) is acceptable at M1 — note it in the
header.

**Test — the oracle**: `tools/worldgen-oracle.ts` runs v1's
`buildWorld` from the repo root in a subprocess (the M0 RNG-oracle
pattern) at matched dims/seed and compares every substrate field:
bit-exact where no dmath swap intervened, ≤1e-6 relative where one did
(ruling 3), with a per-field diff report printed. This is PR evidence.

### 3. The travel-time cost field — `src/sim/travel/`

Port `src/sim/peopleSim/transport.js`'s continuous edge-cost core
(`baseEdgeCost` components: altitude, slope, cold, aridity, river
bonus, coast bonus — the header documents the physics) as the terrain
seed, then re-found and extend per 03.2:

- **Real units.** Edge traversal time in DAYS: distance (km at this
  latitude — cells are not square in km on an equirectangular grid;
  east-west distance scales with cos(lat), via dmath) ÷ mode speed ×
  terrain factor × seasonal factor × infrastructure factor. Every
  constant in real units, converted at km-per-tile; 1-D features
  (river/coast) integrate per real area via the band convention.
- **Modes**: foot, pack animal, cart, river craft, coastal sail,
  open-sea sail. Land modes on land; river craft on river cells above
  a magnitude bar plus lakes, with **asymmetric** cost (downstream
  cheaper than upstream — the engine must support directed costs);
  coastal sail on water within a coast-distance band; open-sea
  everywhere at sea, gated on navigation capability. Mode speeds and
  factors are ledgered constants calibrated from 03.3's anchors
  (foot ~20–30 km/day, ride ~30–40, Duncan-Jones ratios).
- **Season**: factors are functions of the month, read from the
  monthly climate — snow/pass closure by cold, mud seasons, monsoon
  windows and storm seasons at sea, sea ice. Smooth functions of
  climate fields, never threshold buckets keyed to named regions (R2:
  the monsoon must emerge from the wind/moisture data, not from an
  "Indian Ocean" special case).
- **Infrastructure factor**: the term exists in the formula and reads
  a neutral (all-ones) field at M1 — roads and ports are emergent
  stocks that arrive with their milestones. Document the slot.
- **Danger premium**: NOT in M1 (it reads authority, which needs M5).
  Leave the documented slot, no implementation.
- **Freight**: cost = time × mode cost-per-ton-day, anchors ledgered
  (land grain haul e-folds at 340 km — carry the `[CONTESTED]` flag
  into the ledger row; sea:river:land ≈ 1:5:28).

### 4. The CRP routing engine — `rust/router/` becomes real

Delete the M0 Dijkstra fixture and its graph (ratified in
QUESTIONS.md). Build the three-phase engine (DECISIONS 19b) over the
grid topology (8-neighbor, directed, (cell × mode) layers per ruling
6):

- **Preprocess** (once per world): metric-independent — partition the
  topology into nested cells suitable for CRP-style customization.
- **Customize** (per active metric: month + mode set + capability
  set): fill overlay shortcuts from the edge-cost field. On-demand
  with a small cache (ruling 5).
- **Query**: point-to-point (path + days) and multi-source one-to-many
  distance maps (the shape every later consumer — trade, admin reach,
  migration — will read).

Narrow typed-array API across the wasm boundary; f64; fixed iteration
order everywhere (heap ties broken by index — deterministic by
construction, cross-engine identical). If full CRP proves heavier than
the budget allows at M1, a well-partitioned bidirectional Dijkstra
with the same three-phase API is an acceptable first engine — the API
contract and determinism are the deliverable; say so in QUESTIONS.md
and the algorithm upgrade stays invisible to callers.

**Test**: a routing battery (fixed set of ~50 queries across grids,
modes, months) hashed; identical hashes Node + all three browsers (the
tri-engine job extends to run it); plus property tests — triangle
inequality on sampled triples, symmetry where costs are symmetric,
monotonicity (adding a capability never lengthens a journey).

### 5. Conservation accounting, re-founded

Replace per-write attribution with **per-pass aggregated accounting**
(binding ruling, QUESTIONS.md answer 1): a pass declares its channel
once, writes are accumulated per pass at array speed, and the ledger
asserts the same zero-unexplained-flux contract at `endPass`. The
placeholder field migrates to this API; the 6.2 ms/tick M0 cost must
drop to noise. This lands BEFORE real fields arrive at M2 — that is
why it is M1 work.

### 6. The map shell — `src/shell/` grows real

The worker snapshot protocol with pooled transferable buffers (ported
v1 pattern; error containment), a declarative lens registry seeded
with:

- **Terrain lens**: elevation/water/rivers/biome composite.
- **Climate lens**: temperature/moisture, with a **month scrubber**
  (1–12) — seasonality is M1's new physics; make it visible.
- **Travel query**: click two points → route drawn on the map, days
  reported, with mode-capability toggles and the month scrubber
  applied. Powered by the worker + wasm engine (point query).

Minimal chrome, real function — "watchable on screen the day it
lands" is a standing rule. `npm run dev` must demo all three.

### 7. The reality gate — `tools/gate-travel.ts`, wired as `npm run gate`

Implements 03.3's table against a hand-curated fixture
`data/reality/travel-routes.json` (+ `data/reality/README.md` with
per-source citation and licensing — first real content on the dataset
shelf). Routes specified as lat/lon endpoints, month, mode-capability
set, expected days, source, tolerance:

- ORBIS-class route times (Rome→Alexandria, Rome→London, and ~10–15
  more published pairs, transcribed with citations — no scraping
  needed) within ~25%.
- A foot day ~20–30 km, a ride ~30–40 km (emergent from the cost
  field, measured on flat reference terrain).
- Freight ratios sea:river:land ≈ 1:5:28.
- Land grain-haul shed 20–100 km (where freight cost exceeds the
  340 km e-fold's implied viability).
- Monsoon asymmetry: the same Indian-Ocean route pair differs by
  season in the correct direction (this must EMERGE from the monthly
  wind/moisture data — see the R2 note above).
- **Cross-grid real-km parity**: the battery's answers at dev vs
  target agree within 10% per route (initial band; recorded per
  route; ratcheted later, never widened silently).

Gate output: JSON with provenance, one row per check, hard exit code.
CI runs it at both grids.

### 8. Bench + budgets

`tools/bench.ts` extends to the routing phases (preprocess, customize,
query, full battery) and substrate build, at both grids;
`v2/bench-baselines.json` committed; CI compares and fails >20%
regressions (ruling 8). Bench output keeps the provenance stamp.

### 9. CI

`v2-ci.yml` grows: Node job adds `npm run gate` and the bench
regression check; the tri-engine job adds the routing battery hash
(deliverable 4's test). Everything still runs from a clean checkout.
